WordPress Multi-Tier on Kubernetes

A production-like two-tier application — WordPress frontend and MySQL backend — deployed across a 2-node data plane with ConfigMaps, Secrets, and Service discovery.

This guide walks through Lab 41: how a user reaches WordPress through a NodePort Service, how the WordPress Pod connects to MySQL via DNS (mysql:3306), and how ConfigMaps and Secrets inject configuration without hardcoding values in container images.

Multi-Tier Model

What Is a Multi-Tier Application?

Presentation Tier

WordPress — Apache/PHP web server and user interface. Stateless at the Pod level; stores content in the database. Can be scaled horizontally (multiple replicas behind one Service).

Data Tier

MySQL — Relational database storing posts, users, and settings. Stateful; typically one replica in this lab. Not exposed directly to the internet.

Configuration Layer

ConfigMaps hold non-sensitive settings (database name, host, user). Secrets hold passwords. Both inject values as environment variables at Pod startup.

Networking Layer

Services provide stable DNS names and load balancing. WordPress uses the Service name mysql — not a Pod IP — to reach the database through Kubernetes DNS.

Why separate tiers? Each layer can be updated, scaled, and secured independently. The database is never directly exposed to users — only the WordPress Service is reachable from outside the cluster (via NodePort in this lab).

Resource Reference

Kubernetes Objects in This Stack

ConfigMap — mysql-config

MySQL non-sensitive config

Stores MYSQL_DATABASE: database1. Injected via envFrom.configMapRef into the MySQL container. Safe to version-control; change per environment without rebuilding the image.

Secret — mysql-secret

MySQL root password

Stores MYSQL_ROOT_PASSWORD (base64-encoded, not encrypted). Injected via secretKeyRef. Required for MySQL initialization. Protect with RBAC in production.

Deployment — mysql

Database workload controller

Runs one MySQL Pod (replicas: 1). Labels Pod with app: mysql so the Service can find it. Combines ConfigMap + Secret into container environment variables.

Service — mysql

Stable database endpoint

Exposes port 3306 with DNS name mysql. Selector app: mysql maps to Pod Endpoints. WordPress connects here — Kubernetes DNS resolves to ClusterIP automatically.

ConfigMap — wordpress-config

WordPress DB connection settings

Defines WORDPRESS_DB_HOST: mysql (the Service name!), WORDPRESS_DB_USER, and WORDPRESS_DB_NAME. The host value is service discovery — not an IP address.

Secret — wordpress-secret

WordPress DB password

Stores WORDPRESS_DB_PASSWORD. Must match MYSQL_ROOT_PASSWORD in mysql-secret or authentication fails and WordPress shows "Error establishing database connection."

Deployment — wordpress

Frontend workload controller

Runs the WordPress container. On startup, reads env vars, connects to MySQL, and initializes WordPress tables in database1. Can scale to multiple replicas — all share the same database.

Service — wordpress-service

External user entry point

NodePort Service exposing port 80. Users reach WordPress at <node-ip>:<nodePort>. Load-balances across all WordPress Pods matching app: wordpress.

Request Path

End-to-End Communication Flow

1

User hits NodePort

Browser sends HTTP to <node-ip>:30123. Any worker node accepts NodePort traffic and forwards it to the wordpress-service ClusterIP.

2

Service routes to WordPress Pod

wordpress-service selects Pods with app: wordpress. Traffic goes to port 80 on a healthy WordPress Pod (Node 1 in our diagram).

3

WordPress reads config

Container env vars from wordpress-config and wordpress-secret tell WordPress to connect to host mysql, user root, database database1.

4

DNS resolves mysql

WordPress queries CoreDNS. mysql resolves to mysql.default.svc.cluster.local → MySQL Service ClusterIP (e.g. 10.96.123.45).

5

MySQL Service → MySQL Pod

Traffic on port 3306 is forwarded to the MySQL Pod Endpoint on Node 2. Service abstracts away the Pod IP.

6

MySQL stores data

MySQL uses env from mysql-config and mysql-secret. WordPress reads/writes wp_posts, wp_users, and other tables in database1.

Key insight: Users never talk to MySQL directly. Only WordPress Pods connect to the database — through the internal Service name. This keeps the data tier off the public internet.
Manifests

YAML from Lab 41

MySQL ConfigMap + Secret
apiVersion: v1
kind: ConfigMap
metadata:
  name: mysql-config
data:
  MYSQL_DATABASE: "database1"
---
apiVersion: v1
kind: Secret
metadata:
  name: mysql-secret
type: Opaque
data:
  MYSQL_ROOT_PASSWORD: c2ltcGxpZGVhcm4=  # k8slearning
MySQL Deployment + Service
apiVersion: apps/v1
kind: Deployment
metadata:
  name: mysql
spec:
  replicas: 1
  selector:
    matchLabels:
      app: mysql
  template:
    metadata:
      labels:
        app: mysql
    spec:
      containers:
      - name: mysql
        image: mysql:8.0
        envFrom:
        - configMapRef:
            name: mysql-config
        env:
        - name: MYSQL_ROOT_PASSWORD
          valueFrom:
            secretKeyRef:
              name: mysql-secret
              key: MYSQL_ROOT_PASSWORD
---
apiVersion: v1
kind: Service
metadata:
  name: mysql
spec:
  type: NodePort
  selector:
    app: mysql
  ports:
  - port: 3306
    targetPort: 3306

Hands-On

Lab Exercises and Production Notes

Lab 41

Follow the full step-by-step lab: deploy MySQL first, then WordPress, test DNS from inside the WordPress Pod, and complete the browser-based WordPress setup wizard.

Scale WordPress

kubectl scale deployment wordpress --replicas=3 — the Service load-balances across all three Pods. MySQL stays at one replica because it is stateful.

Test persistence

Delete the WordPress Pod — a new one recreates and your posts remain because data lives in MySQL, not in the WordPress container filesystem.

Troubleshoot DNS

kubectl exec -it -l app=wordpress -- nslookup mysql — verify CoreDNS resolves the Service name to a ClusterIP before debugging connection errors.

Production gap

This lab has no PersistentVolume for MySQL — data is lost if the MySQL Pod is deleted. Add a PVC mounted at /var/lib/mysql for production.

Production gap

Replace NodePort with Ingress + TLS for external access. Add NetworkPolicies so only WordPress Pods can reach MySQL on port 3306.
